# Document-grounded warranty and policy assistant

**Status:** proposed (local migration draft awaiting review)  
**Date:** 2026-10-23

ClaimForge will keep document Q&A read-only and grounded in documents explicitly selected by the signed-in owner. Next.js owns authenticated UI, owner/product/document checks, retrieval, and Groq answer generation; Supabase owns Auth/RLS, private files, Postgres search, document/index state, the application-owned processing-job table, Supabase Queues, and a scheduled Edge Function worker. n8n remains inactive and out of the answer path. The approved MVP embedding direction is Supabase Edge Runtime with runtime alias `gte-small`, 384 dimensions, English-only input, a 512-token limit, mean pooling, and normalization. Local worker/provider boundaries are implemented with mocks only; Queue, Edge Runtime, database, scheduling, and transaction integrations remain unverified.

## Current state and constraints

The local implementation extracts native text from PDFs, stores page-aware chunks, retrieves with PostgreSQL English full-text search, and calls the configured Groq chat model. It checks ownership and selected document IDs, validates citation IDs against retrieved rows, and can abstain or report a conflict. These paths have not been verified against live Supabase or Groq. The additive RAG migration is local only. OCR and hybrid retrieval are not implemented. Indexing still runs synchronously in a Next.js route; separate worker and embedding boundary modules now exist under `supabase/functions/_shared`, but they are not wired to Supabase Queues, Storage, Postgres, or a deployed Edge Function. The existing private Storage bucket and owner-scoped document/chunk foundation are described in project docs; confirm production schema and policies before any migration.

Uploaded files, extracted/OCR text, retrieved chunks, and user messages are untrusted data, never instructions. The answer path must search only selected documents belonging to the authenticated user's selected product, validate every rendered citation against retrieved evidence, label document facts/user statements/inferences separately, and abstain or ask for clarification on missing, low-quality, incomplete, or conflicting evidence. It must not send claims or contact companies. RAG does not guarantee coverage or correctness and is not legal advice.

## Embedding and retrieval direction

The approved MVP embedding provider/runtime is the Supabase Edge Runtime and its runtime model alias is `gte-small`. `Supabase/gte-small` is the model repository reference, not the runtime alias. The model is 384-dimensional, English-only, and has a 512-token maximum input. Supabase's vector-column guide links this model and specifies `vector(384)`. The local embedding boundary explicitly requests mean pooling and normalization for both document and query text, and validates 384 finite values. It is a testable boundary, not a live Edge Runtime integration. The reviewed Supabase docs/model card do not identify an immutable model revision; record the model alias/repository and a nullable revision field, and do not fabricate a revision. Pin a source commit/revision only if Supabase exposes one and it is verified during implementation.

Keep English full-text search for exact clause language and use hybrid retrieval with Postgres full-text search plus `pgvector`; Supabase documents this pattern and RLS-based retrieval permissions. Vector similarity is not evidence confidence by itself. Record model ID, nullable revision, dimension (384), pooling (`mean`), normalization (`true`), and index generation with the chunk embedding; constrain retrieval to the active generation/configuration. The model is English-only and truncates inputs beyond 512 tokens. The current chunker does not guarantee token-level limits; token-aware chunk/input validation is still required before processing documents with this embedding path.

Before changing model or dimension, use an expand/backfill/cutover procedure: add a replacement vector column/index if dimensions differ, create a new complete index generation while the old generation remains queryable, verify coverage and retrieval, atomically switch the active generation/model, then remove obsolete data/schema only after a retention window and rollback check. Do not overwrite the only usable embeddings during re-indexing. The model is a local implementation choice; no live provider call or live migration is authorized.

The additive local vector-search migration uses cosine distance (`<=>`) with `vector_cosine_ops` and an HNSW index. Supabase recommends HNSW and documents that `<=>` must be paired with `vector_cosine_ops`; cosine is the safer default when stored/query vectors may not be normalized. The function pushes owner (`auth.uid()`), product, selected document IDs, active index version, and embedding model/options filters into SQL; it runs as `SECURITY INVOKER`, caps results at eight, and truncates returned chunk text to 1,200 characters. The target pgvector version and query plan are unknown without a database, so the index definition is a reviewed draft, not verified against the target.

## Proposed responsibilities and asynchronous strategy

- **Next.js:** authenticated APIs verify the session, product/document ownership, selection, request bounds, and document readiness. The job-creation API derives `user_id` from the verified session and checks ownership with the user's RLS-scoped client; only then does server-only code insert the durable job/outbox row. No browser role can create or mutate jobs. Chat answering remains a separate synchronous Next.js request and never calls the worker or n8n. Upload bytes go directly to private Storage, not through a Vercel Function.
- **Supabase:** Auth/RLS, private Storage, Postgres document/index data, page/section provenance, FTS, the pinned `gte-small` vector column, the application-owned `document_processing_jobs` table, Supabase Queues, and the scheduled Edge Function worker. Queue payloads contain job IDs only; the jobs table remains authoritative for status, idempotency, processing attempts, dispatch state, and safe errors. The Edge Function uses the Supabase Edge Runtime model alias `gte-small` with mean pooling and normalization enabled. Ordinary browser clients can read only their own jobs and cannot create/update/delete them. Worker adapters must verify the job/document relationship before privileged reads or writes.
- **Single scheduling/worker flow:** a Supabase-scheduled Edge Function is the only worker. Supabase Queues are pull-based: the Edge Function runs on a bounded schedule, reconciles pending/expired outbox rows, dispatches due job IDs, then reads a bounded number of queue messages using a visibility timeout. It does not use a Next.js cron route or n8n. Queue API wrappers are not exposed by default, so a future local/live integration must explicitly verify server-only access and grants. Schedule invocation credentials must be stored using the supported secret mechanism (for example Vault), not embedded in migrations or function source.
- **Dispatch and recovery:** claim pending or expired `dispatching` outbox rows with a lease, send `{jobId}` to the queue, and mark dispatch complete. If send fails, return the row to pending with a safe retry schedule; a crash around send can produce duplicates, so dispatch must be idempotent. The worker reads with a visibility timeout and conditionally claims the durable job. On a retryable failure, persist `retry_wait`, bounded attempt count, and `available_at`, reset dispatch state, then acknowledge the current message only after that transition is durable; a later scheduled run redispatches it. On unexpected failure, do not acknowledge; allow visibility-timeout redelivery. On terminal or successful processing, persist the terminal job/index state before acknowledging. Duplicate delivery of a terminal job is acknowledged without reprocessing.
- **Safe publication and database guarantees:** write chunks/embeddings under a new, inactive `target_index_version`; never delete or overwrite the currently active version during preparation. Publish only after all extraction and embeddings validate. The final operation must atomically switch `product_documents.index_version`/`ingestion_status` and mark the job succeeded. Job claiming, retry transitions, outbox leasing, and publication therefore require narrow database-side atomic functions or equivalent transactions. The current local migration defines tables and indexes but not those functions or Queue grants; mocked orchestration cannot prove concurrency, transaction atomicity, RLS, or queue visibility semantics.
- **Local operation:** without Docker or a local Supabase stack, test only the orchestration and provider boundaries with synthetic fixtures and mocked adapters. Do not access the live project, schedule/deploy a function, or process real documents. Live/local Edge Runtime, Queue, database and scheduling integration remain unverified.
- **n8n:** no role in ingestion, queue dispatch/consumption, reconciliation, or chat. Keep both workflows inactive and unchanged. Never send document bytes, OCR/chunk text, prompts, personal details, signed URLs, or secrets to n8n.

### Proposed local implementation plan

The job API already exists at `POST /api/products/[id]/documents/[documentId]/processing` and its GET counterpart. It verifies ownership, uses a server-only client for job creation, and reports pending dispatch. The current synchronous index route remains a local prototype; it is not the asynchronous worker.

The implementation boundary is `supabase/functions/_shared/document-processing-worker.ts`: claim one job, prepare complete pages/chunks, embed the complete chunk set, stage it under `target_index_version`, and call an atomic publication adapter. A Queue adapter reads only bounded job-ID messages with visibility timeout and acknowledges only after the handler returns from a durable state transition. Scheduled Supabase Edge Function invocation handles both outbox reconciliation and Queue consumption; no Next.js cron route is part of this design. `supabase/functions/_shared/embeddings.ts` defines the server-side `gte-small` API contract and can use the Supabase Edge Runtime session.

The current coding pass tests those orchestration/provider contracts with synthetic fixtures and mocked boundaries only. It does not implement or claim actual Queue/Storage/Postgres adapter wiring, scheduled invocation, atomic RPCs, RLS behavior, or Edge Runtime connectivity. Before those integrations are wired, the local migration will need reviewed atomic claim/retry/publication functions and explicitly scoped Queue access. A failed or partial new generation must never change the currently published `index_version`.

**User-visible states:** `queued` (including outbox dispatch pending), `processing`, `retry_wait` (“Retry scheduled”), `needs_review` (“Review document”), `succeeded` plus document `indexed` (“Ready”), and `failed` (“Could not process” with a safe retry/help action). Keep internal dispatch states, leases, provider errors, and raw exception text out of the UI. The existing owner-scoped status API remains the status-read seam.

The runtime still needs a verified invocation schedule, Queue grants and wrapper exposure, server-only credential setup, bounded Edge Function duration, and transactional database functions before deployment or local Supabase integration. Do not configure or deploy any of these in this local-only pass.

## Revised local schema plan (not SQL)

The existing local RAG migration already adds `ingestion_status`, safe warning code, `indexed_at`, and document `index_version`; chunks gain `section_path`, `chunk_index`, extraction confidence, content hash, and index version. Preserve these additive fields and the existing page number. Before finalizing SQL, verify constraints and trusted write privileges against the selected worker design.

Proposed chunk additions: nullable `embedding extensions.vector(384)` for pre-existing/unembedded rows; `embedding_provider` (`supabase_edge_runtime`); `embedding_model_alias` (`gte-small`); `embedding_model_repository` (`Supabase/gte-small`); nullable `embedding_model_revision` (no immutable revision was found in the reviewed Supabase docs/model card); and `embedding_dimension` (384). The local embedding boundary uses mean pooling and normalization, so populated vectors should record `embedding_pooling = 'mean'` and `embedding_normalized = true`. All populated vectors must belong to the active index generation/model. Preserve extraction provenance separately; don't store raw provider responses.

Proposed `document_processing_jobs` fields: `id`, `user_id`, `document_id`, `target_index_version`, `idempotency_key`, `status`, `dispatch_status`, `dispatch_attempt_count`, `dispatch_lease_expires_at`, `dispatched_at`, `attempt_count`, `max_attempts`, `available_at`, `lease_expires_at`, `safe_error_code`, `created_at`, `updated_at`, `started_at`, and `completed_at`. Enforce owner/document consistency with `(document_id, user_id)` referencing the existing unique document key; make `(user_id, idempotency_key)` unique and prevent duplicate active `(document_id, target_index_version)` jobs. The Next.js server validates ownership and creates the durable job/outbox row; the scheduled Edge Function reconciles and dispatches due jobs. The table is the source of truth; Queue payloads contain only job IDs. The owner can read only their job rows via RLS; browser clients have no job INSERT/UPDATE/DELETE privileges. A trusted worker write path must be narrowly granted; privileged Supabase keys bypass RLS and must remain server-only. No chat persistence table is proposed; current chat history remains transient.

Indexes: retain the existing GIN full-text index and B-tree `(document_id, user_id, index_version)` for selected document/generation filtering; do not add the alternate `(user_id, document_id, index_version)` index because it would duplicate the same equality lookup. The additive local vector-search migration drafts an HNSW index using `vector_cosine_ops` for the `<=>` operator. Supabase docs recommend HNSW and specify the operator/opclass pairing; the target pgvector version, index creation, and query plan cannot be checked without a database. HNSW is approximate and selective metadata filters may return fewer than the requested limit; test the plan and recall when local Supabase is available. Retain a unique job idempotency index plus `(user_id, status, updated_at)`, `(status, available_at)`, and an outbox reconciliation index. Do not rely on any search index as an ownership boundary.

Retain the composite owner foreign-key pattern and cascading deletion for document descendants/jobs. Deleting database metadata does not remove the private Storage object, so object deletion/cleanup must be coordinated separately. For model changes, preserve the active generation while backfilling a new one; if dimensions differ, add a replacement vector column/index for expand/backfill/cutover, verify it, switch atomically, and retire the old column only after rollback is no longer needed.
