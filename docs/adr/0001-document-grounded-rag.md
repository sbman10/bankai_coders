# Document-grounded warranty and policy assistant

**Status:** proposed (local migration draft awaiting review)  
**Date:** 2026-10-23

ClaimForge will keep document Q&A read-only and grounded in documents explicitly selected by the signed-in owner. The proposed boundary is Next.js for authenticated UI, owner/product/document checks, retrieval, and Groq answer generation; Supabase for Auth/RLS, private files, Postgres search, document/index state, an application-owned processing-job table, and Supabase Queues for delivery/retries; n8n remains inactive and out of the answer path. The approved MVP embedding direction is Supabase Edge Runtime with runtime alias `gte-small`, 384 dimensions, English-only input, and a 512-token limit. The proposed worker flow is a single Vercel Cron → protected Next.js worker route, with embedding delegated to a Supabase Edge Function; local invocation, deployment prerequisites, OCR provider, and residency remain unresolved.

## Current state and constraints

The local implementation extracts native text from PDFs, stores page-aware chunks, retrieves with PostgreSQL English full-text search, and calls the configured Groq chat model. It checks ownership and selected document IDs, validates citation IDs against retrieved rows, and can abstain or report a conflict. These paths have not been verified against live Supabase or Groq. The additive RAG migration is local only. OCR, embeddings, hybrid retrieval, and durable asynchronous ingestion are not implemented. Indexing currently runs synchronously in a Next.js request. The existing private Storage bucket and owner-scoped document/chunk foundation are described in project docs; confirm production schema and policies before any migration.

Uploaded files, extracted/OCR text, retrieved chunks, and user messages are untrusted data, never instructions. The answer path must search only selected documents belonging to the authenticated user's selected product, validate every rendered citation against retrieved evidence, label document facts/user statements/inferences separately, and abstain or ask for clarification on missing, low-quality, incomplete, or conflicting evidence. It must not send claims or contact companies. RAG does not guarantee coverage or correctness and is not legal advice.

## Embedding and retrieval direction

The approved MVP embedding provider/runtime is the Supabase Edge Runtime and its runtime model alias is `gte-small`. `Supabase/gte-small` is the model repository reference, not the runtime alias. The model is 384-dimensional, English-only, and has a 512-token maximum input. Supabase's vector-column guide links this model and specifies `vector(384)`. Its model card JavaScript examples use Transformers.js feature extraction with `pooling: 'mean'` and `normalize: true`; these are **proposed settings only**, not finalized implementation behavior. **No embedding function currently exists in ClaimForge**, so there is no current pooling/normalization behavior to report. Verify and explicitly configure those settings in the implementation before persisting those metadata values. The reviewed Supabase docs/model card do not identify an immutable model revision; record the model alias/repository and a nullable revision field, and do not fabricate a revision. Pin a source commit/revision only if Supabase exposes one and it is verified during implementation.

Keep English full-text search for exact clause language and use hybrid retrieval with Postgres full-text search plus `pgvector`; Supabase documents this pattern and RLS-based retrieval permissions. Vector similarity is not evidence confidence by itself. Record model ID, nullable revision, dimension (384), pooling (`mean`), normalization (`true`), and index generation with the chunk embedding; constrain retrieval to the active generation/configuration. The model is English-only and truncates inputs beyond 512 tokens, so chunking and question embedding must enforce this limit explicitly.

Before changing model or dimension, use an expand/backfill/cutover procedure: add a replacement vector column/index if dimensions differ, create a new complete index generation while the old generation remains queryable, verify coverage and retrieval, atomically switch the active generation/model, then remove obsolete data/schema only after a retention window and rollback check. Do not overwrite the only usable embeddings during re-indexing. The model is a local implementation choice; no live provider call or database migration is authorized.

## Proposed responsibilities and asynchronous strategy

- **Next.js:** authenticated APIs verify the session, product/document ownership, selection, request bounds, and document readiness. The job-creation API derives `user_id` from the verified session and checks ownership with the user's RLS-scoped client; only then does server-only code insert the job/outbox row. No browser role can create or mutate jobs. A single protected worker route owns queue dispatch, queue consumption, status updates, and outbox reconciliation. Chat answering remains a separate synchronous Next.js request and never calls the worker or n8n. Upload bytes go directly to private Storage, not through a Vercel Function.
- **Supabase:** Auth/RLS, private Storage, Postgres document/index data, page/section provenance, FTS, the pinned `gte-small` vector column, and the application-owned `document_processing_jobs` table. Supabase Queues carry job IDs and supply visibility timeout/re-delivery; the jobs table remains authoritative for status, idempotency, processing attempts, dispatch state, and safe errors. The embedding call alone runs in a secured Supabase Edge Function using the Supabase Edge Runtime model alias `gte-small`. Ordinary browser clients can read only their own jobs and cannot create/update/delete them. Next.js and the Edge Function use server-only credentials and validate the job/document relationship before privileged reads or writes.
- **Single scheduling/worker flow:** use one Next.js App Router route, proposed as `GET /api/internal/document-processing/worker`, configured as the Vercel Cron target when a deployment is later approved. Vercel Cron authenticates with `Authorization: Bearer <CRON_SECRET>`; the route fails closed if missing/invalid and processes a bounded batch. Do not also schedule a Supabase Edge Function or use Supabase Cron/`pg_net` for this worker. Supabase's schedule guide warns that a secret used in a pending `pg_net` request is readable to database login roles until sent; avoiding that second scheduler removes that exposure and the dual-scheduler ambiguity.
- **Dispatch and recovery:** each run first scans the outbox for due `pending` or expired `dispatching` rows, claims them with a short lease, sends only `{jobId}` to a durable Basic Supabase Queue, then marks dispatch complete. A send failure leaves/reverts the row to pending with a safe error and next-attempt time. A crash before send leaves an expiring lease; a crash after send but before marking can enqueue a duplicate. The next Vercel Cron run re-scans outstanding rows; it does not rely on Vercel retrying missed/failed cron invocations, because Vercel documents cron delivery as best-effort and potentially duplicate. The job idempotency key plus conditional job claim makes duplicate dispatch safe. Each run then reads queue messages with a visibility timeout and conditionally claims the corresponding due job. On known retryable failure, it stores `retry_wait` plus a backoff `available_at`, resets dispatch to pending, and acknowledges the current message only after that state is durable; a later run redispatches it. On an unexpected crash, it does not acknowledge, so the Queue makes the message visible again after the visibility timeout. On success/terminal failure, it commits job/document state before archiving/deleting the message; redelivery of an already-terminal job only acknowledges the duplicate. Cap processing attempts and batch size. Keep extraction/model work bounded to one or a small number of jobs per invocation within the configured function duration.
- **Local operation:** Vercel documents no framework-native local Cron support. During local-only implementation, invoke the same protected worker route manually with synthetic fixtures; do not configure/deploy a Cron schedule yet. The later deployed schedule and `CRON_SECRET` setup require separate deployment approval.
- **n8n:** no role in ingestion, queue dispatch/consumption, reconciliation, or chat. Keep both workflows inactive and unchanged. Never send document bytes, OCR/chunk text, prompts, personal details, signed URLs, or secrets to n8n.

### Proposed local implementation plan

The current workspace listing did not expose existing route files under `apps/web/src/app/api`; treat these paths as proposed and reconcile them against the actual route layout before coding. Implement one public job API pair and one internal worker route:

1. `POST /api/products/[productId]/documents/[documentId]/processing-jobs`: verify session with `getUser`, load product and document through the user's RLS-scoped client, verify both ownership and product linkage, accept a UUID idempotency key, and create/read the job using a server-only client. Do not accept `user_id` from request data. Repeating the key returns the existing job; enforce one active job per document/index generation.
2. `GET /api/products/[productId]/documents/[documentId]/processing-jobs/[jobId]`: authenticated owner-scoped status read, with product/document/job linkage checks; return only safe status and error codes.
3. `GET /api/internal/document-processing/worker`: verify `CRON_SECRET` in constant time; dispatch pending/expired outbox rows, consume a bounded number of Queue messages, atomically claim each job, extract the owned private object, call a server-authenticated Edge Function for `gte-small` embeddings, persist page/section-provenanced chunks, and acknowledge only after durable job state is stored. Job messages contain IDs only. Never log document content or embeddings.
4. `supabase/functions/embed-text/index.ts`: server-to-server authenticated Edge Function using the Supabase Edge Runtime `gte-small` alias. Verify supported runtime API and explicit pooling/normalization settings during implementation; the current ADR keeps them proposed.
5. **User-visible states:** map the durable job/document state to clear UI labels: `queued` (including outbox dispatch pending), `processing`, `retry_wait` (“Retry scheduled”), `needs_review` (“Review document”), `succeeded` plus document `indexed` (“Ready”), and `failed` (“Could not process” with a safe retry/help action). Keep internal dispatch states, lease details, provider errors, and raw exception text out of the UI. Poll the owner-scoped status route until a terminal/review state.

Use vertical TDD at these public seams with synthetic owners/documents: unauthenticated and cross-owner rejection; wrong product/document linkage; idempotent duplicate job request; dispatch interruption before/after queue send; duplicate cron run and duplicate queue delivery; lease expiry/retry/exhaustion; success, unreadable-document review, and safe failure status; and status isolation in the UI. Mock external boundaries only. Read the applicable Next.js 16 docs before changing route handlers.

No resource is created by this plan. Supabase's Queues quickstart says Queues are pull-based, Basic Queues are logged/durable, and queue APIs are not exposed through the Data API by default; using the `pgmq_public` wrappers requires enabling exposure and setting function/table-role permissions. Before implementation, decide/verify that server-only access is enabled for `service_role` while `anon` and `authenticated` remain ungranted. Vercel Cron configuration/secret, Edge Function authentication, worker execution limits, retry timing, and safe service-role handling must be reviewed before deployment or live-service setup.

## Synthetic-document bake-off and evaluation

Use synthetic documents and accounts only. Create a versioned set containing native-text and scanned PDFs; rotated/low-quality pages; tables; clauses with exclusions, exceptions, and conditions; definitions referenced across pages; missing pages/endorsements; conflicting versions/dates; paraphrased and exact-term questions; irrelevant questions; and adversarial instructions embedded in documents. Label the expected evidence spans, pages/sections, answerability, conflicts, and expected abstention before running candidates.

Compare native extraction and the approved OCR candidates on page/section provenance, text quality, table/reading-order preservation, quality warnings, failure behavior, latency, and cost per page. Compare current FTS against each approved embedding candidate and hybrid retrieval using evidence Recall@k, citation validity, and retrieval latency. Evaluate generated responses for supported claims, fact/inference separation, abstention correctness, conflict handling, prompt-injection resistance, and citation support. Manually review representative failures. Report sample size and measured results; set acceptance thresholds with the product owner before judging results. Automated judges are diagnostic signals, not proof of safety. Do not use real customer documents or claim a provider wins before the bake-off.

## Revised local schema plan (not SQL)

The existing local RAG migration already adds `ingestion_status`, safe warning code, `indexed_at`, and document `index_version`; chunks gain `section_path`, `chunk_index`, extraction confidence, content hash, and index version. Preserve these additive fields and the existing page number. Before finalizing SQL, verify constraints and trusted write privileges against the selected worker design.

Proposed chunk additions: nullable `embedding extensions.vector(384)` for pre-existing/unembedded rows; `embedding_provider` (`supabase_edge_runtime`); `embedding_model_alias` (`gte-small`); `embedding_model_repository` (`Supabase/gte-small`); nullable `embedding_model_revision` (no immutable revision was found in the reviewed Supabase docs/model card); and `embedding_dimension` (384). Pooling and normalization metadata remain nullable/proposed until the implementation is verified; the model card shows mean pooling and optional L2 normalization, while the Supabase example enables both. All populated vectors must belong to the active index generation/model. Preserve extraction provenance separately; don't store raw provider responses.

Proposed `document_processing_jobs` fields: `id`, `user_id`, `document_id`, `target_index_version`, `idempotency_key`, `status`, `dispatch_status`, `dispatch_attempt_count`, `dispatch_lease_expires_at`, `dispatched_at`, `attempt_count`, `max_attempts`, `available_at`, `lease_expires_at`, `safe_error_code`, `created_at`, `updated_at`, `started_at`, and `completed_at`. Enforce owner/document consistency with `(document_id, user_id)` referencing the existing unique document key; make `(user_id, idempotency_key)` unique and prevent duplicate active `(document_id, target_index_version)` jobs. The Next.js server validates the signed-in user and owned document before using server-only write credentials to create a job and dispatch its minimal identifier to the queue. The outbox fields allow reconciliation after partial dispatch failures; queue/worker operations must be idempotent. The table is the source of truth; Queue payloads contain only job ID/minimal dispatch data. The owner can read only their job rows via RLS; browser clients have no job INSERT/UPDATE/DELETE privileges. A trusted worker write path must be narrowly granted; privileged Supabase keys bypass RLS and must remain server-only. No chat persistence table is proposed; current chat history remains transient.

Indexes proposed: retain the existing GIN full-text index and existing B-tree `(document_id, user_id, index_version)` for selected document/generation filtering; do not add the alternate `(user_id, document_id, index_version)` index because it would duplicate the same equality lookup. The local draft adds no vector index because extension/index support has not been verified locally; consider one only after that verification and representative scale testing. Retain a unique job idempotency index plus `(user_id, status, updated_at)`, `(status, available_at)`, and an outbox reconciliation index. Do not rely on any search index as an ownership boundary.

Retain the composite owner foreign-key pattern and cascading deletion for document descendants/jobs. Deleting database metadata does not remove the private Storage object, so object deletion/cleanup must be coordinated separately. For model changes, preserve the active generation while backfilling a new one; if dimensions differ, add a replacement vector column/index for expand/backfill/cutover, verify it, switch atomically, and retire the old column only after rollback is no longer needed.
