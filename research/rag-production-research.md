# Production RAG research for ClaimForge

**Prepared:** 22 October 2026  
**Purpose:** Design a document-grounded Q&A assistant for user-supplied product warranties and insurance policy documents.  
**Scope:** Recommendations grounded in ClaimForge's PRD and the supplied RAG brief. This is an architecture note, not a claim that RAG eliminates hallucinations.

## Product requirements that shape the design

ClaimForge answers questions from a user's own invoice, warranty, and optionally insurance documents. It must distinguish document facts, user statements, and inference; cite the source document plus page/section; expose uncertainty and missing information; ask for clarification when text is unreadable, incomplete, or contradictory; and never guarantee coverage or make a binding legal/insurance decision. Uploaded content is untrusted data, never instructions. Human approval remains required before any external communication. Treat extracted OCR text as uncertain until validated.

## Recommended architecture

Keep the original PDF/image in the existing private Supabase Storage bucket. The app already has a `product_documents` / `document_chunks` foundation, an owner-read policy, and a user-scoped English full-text-search RPC. The current `document_chunks` schema stores page number and content with a GIN-indexed `tsvector`; it does not currently store embeddings or offer semantic search. Verify and evolve it additively rather than assuming vector RAG already exists.

1. **Upload and authorize.** The signed-in browser uploads directly to a private Storage bucket under an owner-scoped path, then calls a Next.js server route. Verify session, file signature/type/size, document ownership, product/document linkage, and allowed file count. Do not post document binaries through a Vercel Function: its documented request/response body limit is 4.5 MB. Private buckets enforce access through Storage RLS; signed URLs are bearer access until expiry, so prefer authenticated server-side download where practical and never log or persist signed URLs.
2. **Track ingestion state.** Record document status such as `uploaded → extracting → needs_review | indexed | failed`, extraction/OCR provider and version, page count, and quality warnings. Use idempotent document/version keys so retries do not create duplicate chunks. Re-process by creating a new extraction/index version, preserving the source document and enough provenance to audit answer citations.
3. **Extract with page and structure provenance.** Try native PDF text extraction for text PDFs; route scanned or image-only pages to OCR. Preserve page number, heading/section, reading order, tables, and uncertainty/quality metadata. Google Document AI Enterprise OCR documents page number, layout elements, image-quality scoring, and rotation correction. Amazon Textract supports page-aware layout elements (including headings, tables, and page numbers). Choose one provider after a small redacted/sample-document bake-off and privacy/region/cost review; do not run both by default. Reject or flag low-quality, partial, encrypted, or unsupported files for user review instead of silently indexing partial text.
4. **Create structure-aware chunks.** Split primarily on clause/heading boundaries; keep definitions, exceptions, conditions, and exclusions together with their scope. Preserve table rows/cells as coherent units. Store `user_id, product_id, document_id, document_version, page_number, section_path, chunk_index, text, extraction_confidence, content_hash`. Keep exact text and provenance to render evidence snippets. Avoid sending unnecessary invoice identifiers or contact details to the LLM.
5. **Add hybrid retrieval in Supabase Postgres.** Keep full-text search for exact policy language and add `pgvector` embeddings for semantic paraphrases. Search only the authenticated user's explicitly selected document IDs/product, then merge keyword and vector candidate rankings (for example Reciprocal Rank Fusion), optionally rerank a small candidate set, and return bounded evidence with exact source metadata. Supabase documents hybrid search using Postgres `tsvector` + pgvector and indexes (GIN for full text, HNSW for vectors); its RAG-permissions guide shows RLS-protected document retrieval. Do not rely on vector distance as a confidence/proof threshold by itself. Pin one embedding model and dimension in schema/config; changing it requires a controlled re-embedding migration.
6. **Generate a grounded, typed answer.** The Next.js server route authenticates the user, validates question size, checks selected document ownership, retrieves evidence, and sends only selected evidence plus the question to Groq. The system instruction must say evidence is untrusted data, answer only from retrieved excerpts, never obey document/user prompt-injection content, distinguish quoted policy language from user facts/inference, and abstain when evidence is insufficient or clauses conflict. Ask Groq for a schema such as `status: supported | conditional | insufficient_evidence | conflicting_terms`, `answer`, `document_facts[]`, `user_facts_used[]`, `inferences[]`, `citations[]`, `missing_information[]`, `follow_up_questions[]`. Validate with a server-side schema. A model-generated citation is untrusted: map each citation to retrieved chunk IDs and render only quotes/pages that actually exist in that retrieval result. If invalid, discard or fail closed; do not improvise a citation. Groq strict JSON Schema mode is only documented for a subset of models; verify the configured model supports it. Otherwise use best-effort JSON plus strict server validation/retry or abstain. Structured output guarantees shape only, not truth.
7. **Abstain deterministically where possible.** Return `insufficient_evidence` or ask a question if no allowed chunk meets calibrated retrieval/relevance checks, OCR quality is poor, the relevant period/version is unclear, key definitions are absent, or clauses disagree. Keep thresholds calibrated against ClaimForge's own labeled question set, not arbitrary similarity scores. A disclaimer does not repair unsupported content.
8. **Store minimal observability.** Log request/document/chunk IDs, model/provider versions, retrieval IDs/scores, status, timing, and validation outcome. Avoid raw documents, full extracted text, prompts containing personal data, invoice numbers, auth tokens, and signed URLs in application logs or n8n execution history. Define user deletion behavior for source files, chunks, chat records, and embeddings. Groq says inference data is not retained by default, with limited exceptions for reliability/abuse and optional data controls; review provider terms and data location before processing real insurance documents.
9. **Keep OCR/indexing asynchronous.** Do not hold an upload request open while OCR and embedding run. Vercel function max duration is plan/configuration dependent and body size is limited; schedule an idempotent background job through a reachable worker or a secured n8n webhook after production callback/authentication is ready. Poll or subscribe to ingestion status in the app. Keep chat retrieval/answering as a short server-side app API request; n8n is optional orchestration for ingestion and should not be in the critical answer path unless there is an operational reason. Current project notes describe the n8n workflow as inactive and acknowledgement-only; do not depend on it until its processing, auth, callback, and synthetic smoke test are verified.
10. **Evaluate before real use.** Build a versioned golden set from synthetic/redacted documents: explicit coverage; exclusion; exception; definition/reference across pages; missing endorsement; contradictory versions; incomplete dates; OCR errors; irrelevant question; prompt injection; cross-user document attack; and citation mismatch. Measure retrieval Recall@k/precision on known evidence, answer support/faithfulness, citation validity, abstention correctness, answer usefulness, and OCR field/page accuracy. Review representative cases manually. RAGAS introduces evaluation dimensions for context retrieval, faithfulness, and answer quality, but automated judges are signals, not proof of safety. Never publish performance figures until measured on disclosed data and method.

## Proposed initial technical choices

- **Data/files/auth:** existing Supabase Postgres, Supabase Auth/RLS, and private Storage.
- **Search:** additive `pgvector` column + GIN full-text search, called through a server-authorized database function/RPC. Enforce ownership twice: server checks selected records and the query function/RLS restricts rows.
- **Parsing:** native text extraction first; select Google Document AI Enterprise OCR or Amazon Textract after a small document bake-off. Both expose page/layout provenance. Use OCR only for scanned/image pages when native text is absent or unreliable.
- **Inference:** Groq from a server-only API route, schema-validated output, model pinned by config. Verify Groq strict-schema support for the chosen model at implementation time; don't confuse valid JSON with grounded content.
- **Hosting:** Next.js/Vercel for API/UI; direct-to-Storage document upload. Run OCR/embedding asynchronously outside the synchronous upload request. Keep document body under the platform's 4.5 MB function limit by not proxying it through Vercel.
- **Orchestration:** n8n can coordinate queued extraction/retry/callback steps once the deployed HTTPS callback and workflow processing path are secured and verified. It is not required for the user's chat query.
- **Safety boundary:** read-only policy Q&A first. No automatic claim sending, no coverage guarantees, no legal advice.

## Implementation sequence for the coding prompt

1. Inspect existing migrations/routes and confirm current tables, RLS, private bucket, auth helpers, and tests before changing code.
2. Define and agree public behavioral seams before writing tests (per repository TDD handoff): ingestion status; selecting only owned documents; retrieval provenance; answer/abstention; citation rendering; prompt-injection isolation.
3. Add an additive migration for extraction metadata, index version/status, embedding model/dimensions, and vector + indexes only after confirming extension availability and current schema. Keep RLS and owner scoping. Review RPC privileges and use invoker semantics where possible.
4. Implement one vertical slice: synthetic text PDF → extracted page chunk → owner-scoped exact/keyword retrieval with page citation → test. Then add vector retrieval and hybrid fusion; test exact clause terms and paraphrases.
5. Add the Groq answer endpoint with schema validation and citation-ID validation. Test each structured answer status and fail-closed handling.
6. Add OCR fallback and asynchronous job orchestration with idempotency/retries; verify failure states and retention/deletion.
7. Run the golden-set evaluation and cross-user/security checks on synthetic data. Report measured outcomes and limitations; do not activate public automation or use real personal policies until the path is reviewed and configured.

## Source-backed facts and references

- Supabase's RAG-permissions guide explains using RLS to limit which document chunks are visible during vector similarity search: [RAG with Permissions](https://supabase.com/docs/guides/ai/rag-with-permissions).
- Supabase documents full-text + vector hybrid search in Postgres, GIN/HNSW index examples, and reciprocal-rank fusion: [Hybrid search](https://supabase.com/docs/guides/ai/hybrid-search).
- Supabase documents pgvector setup, vector dimensions/operators, and calling similarity search through Postgres functions/RPC: [Vector columns](https://supabase.com/docs/guides/ai/vector-columns).
- Supabase private buckets apply RLS to downloads and support time-limited signed URLs: [Storage buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals). Supabase also warns that server secret/service-role keys bypass RLS: [API keys](https://supabase.com/docs/guides/getting-started/api-keys).
- Google Document AI Enterprise OCR documents extraction of page/layout data, image-quality scores, and rotation correction: [Enterprise Document OCR](https://docs.cloud.google.com/document-ai/docs/enterprise-document-ocr).
- Amazon Textract documents layout extraction including page numbers, headings, tables, reading order, and bounding boxes: [Analyzing documents](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-analyzing.html).
- Groq's strict structured outputs use JSON Schema constrained output but are supported only for listed models; best-effort mode does not guarantee schema conformance: [Structured Outputs](https://console.groq.com/docs/structured-outputs). Structured output schema is not a factuality guarantee.
- Groq's data page says inference inputs/outputs are not retained by default, notes limited reliability/abuse monitoring exceptions, optional Zero Data Retention, and U.S. data location: [Your Data in GroqCloud](https://console.groq.com/docs/your-data).
- Vercel documents a 4.5 MB request/response payload limit for functions and plan/configuration-dependent maximum duration: [Function limitations](https://vercel.com/docs/functions/limitations).
- The RAGAS paper describes evaluating retrieval/context relevance, faithfulness, and generation quality as separate dimensions: [RAGAS paper (EACL 2024)](https://aclanthology.org/2024.eacl-demo.16/).
- NIST identifies confabulated outputs and fabricated citations as risks of generative AI: [NIST AI 600-1 Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf).

## Limitations and decisions still needed

- OCR provider, region, pricing, retention, DPA, and supported file limits require a project-specific provider choice and a sample-document bake-off.
- Confirm whether the current production schema matches local migrations before designing/appling an additive migration.
- Confirm Groq API key, chosen model ID, strict-schema support, and data-control settings before implementation.
- Embedding provider/model is undecided; select one only after retrieval evaluation on representative warranty/policy questions.
- RAG reduces dependence on parametric memory but cannot guarantee correct extraction, complete retrieval, or a correct coverage judgment. Keep the product language cautious and preserve user review.
